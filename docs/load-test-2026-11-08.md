# Load test, 2026-11-08 (production, mock models)

Driver: `scripts/load-test.mjs` (reusable; see the header for its settings). Raw numbers: `load-test-2026-11-08-report.json`.
Cost: none (mock models only). All test data (matches, account, model, sessions) was deleted afterwards.

## What was run
- **40 concurrent browsing visitors** the whole time (persistent sessions, 1-3 s think time; weighted mix of home, benchmarks, docs,
  the matches list, replay pages, the events API and incremental `?after=` polling). 45 s browsing-only baseline first.
- **105 matches created through the real create form** in two waves (70, then 35 two minutes later) from 5 logged-in sessions:
  30 chess games on a simulated slow provider (1.5 s per move, about 5 minutes each, so they must hand off between slices),
  30 six-seat poker hands and 15 three-seat blackjack hands on the same slow provider, 15 instant chess games and 15 chutes & ladders.
  The first wave (70) exceeded the concurrency cap of 50 on purpose. Plus 2 smoke-test matches from earlier.
- Total 8.8 minutes, about 21 moves/s and 27 events/s written on average (10,163 moves, 12,908 events).

## Results
| | Result |
|---|---|
| Matches | **107 / 107 completed**, 0 failed, 0 cancelled, 0 orphaned, 0 move failures |
| Integrity audit | **0 problems**: every match has a gap-free event sequence, a contiguous move log, scored participants, no lease left behind |
| Slice hand-offs | 28 matches needed 2 slices (every slow chess game that crossed the 285 s boundary); all chained and finished. Server logs: 28 `yielded`, 54 `completed`, 0 errors, 0 warnings |
| Hand-off overhead | slow chess median 306 s against an ideal 300 s (200 moves x 1.5 s): about 2% |
| Website under load | 8,181 requests, **0 errors**. p50 85 ms, p95 313 ms, p99 754 ms, max 1.5 s. Baseline was p50 113 ms, p95 307 ms, p99 421 ms |
| Slowest page under load | `/` p95 501 ms, `/matches` p95 423 ms, replay page p95 368 ms; events API p95 54 ms |
| Admission control | peak 52 running at once against a cap of 50 (see below); excess matches waited a median 0 s, p95 27 s, max 29 s |
| Database | peak 11 connections (Neon pooler) with up to 52 concurrent runners |
| Creating a match | 105 / 105 accepted; p50 2.3 s, p95 3.7 s |

## Findings worth acting on
1. **The concurrency cap is soft.** Peak 52 against 50: several simultaneous start requests all see "49 running" and proceed. The overshoot
   is small (4%) and harmless at this scale, but a hard cap needs the count and the lease taken in one atomic statement.
2. **Creating a match takes 2-4 s.** Likely cause (not measured separately): the request waits for the first slice dispatch, which can hit a
   cold runner function. Dispatching in the background (`waitUntil`) would make the click-to-redirect fast; the sweeper already repairs a lost dispatch.
3. **Tail latency grows under load** (p99 421 to 754 ms, max 1.5 s) while the median and p95 do not. Worth watching, not worrying about yet.

## What this does not prove
- **Mock models, not real providers.** No real network variance, no provider rate limits (the 429 and throttle paths were exercised in tests but not
  at scale in production), no token costs, no long outputs.
- **One load generator, one location**, run from a development machine that was also running local builds and tests, so client-side latencies are
  if anything slightly pessimistic.
- **Moderate load, not a breaking point.** About 17 browsing requests/s plus 50 concurrent matches; there was no ramp-to-failure run, and the database is on Neon's free plan.
- **Mostly anonymous browsing**; logged-in pages (admin, chat) were not part of the mix.
- **No failure injection at scale.** The recovery path (sweeper resuming a runner that died) was not triggered in this run: 0 matches needed it.
- The log export was capped at 5,000 lines, so the server-side slice statistics cover roughly the second half of the run.
